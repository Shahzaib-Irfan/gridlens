# GridLens

**Grounded LLM incident reports from smart-meter event streams.**

A utility head-end system emits thousands of raw meter events an hour: `power_failure`, `terminal_cover_opened`,
`voltage_sag`, `neutral_missing`. An operator at 3 a.m. needs something else: *"Transformer TX-0601 has lost its
neutral. Six customers are affected and nothing has been restored. Send a crew."*

GridLens turns the first into the second, and is built so that the model cannot quietly make things up.

```
events (Kafka / head-end export)
   │
   ▼
grouping.py ── deterministic: cluster by transformer and time, keep outages open until power returns,
   │           merge simultaneous transformer outages on one feeder
   ▼
IncidentFacts ── counts, durations, voltages, restoration state, share of the transformer affected
   │
   ▼
summarize.py ── LLM writes a structured report (JSON schema)
   │   ├─ parse + validate against the schema
   │   ├─ grounding check: every meter ID, count and "restored" claim must match the facts
   │   ├─ on failure: send the specific problems back to the model and retry
   │   └─ still failing: fall back to the rule-based report, so operators never get nothing
   ▼
IncidentSummary ── title, severity, probable cause, plain-English summary, evidence, action
```

## Why it is built this way

- **The model never sees raw events.** It sees facts computed by code that has unit tests. Every number in a
  report can be traced back.
- **Hallucinations are checked, not hoped away.** `check_grounding` rejects invented meter IDs, wrong meter
  counts, and claims that supply was restored when it was not. The rejection reasons go back to the model.
- **A rule-based baseline is both the fallback and the bar to beat.** If the LLM can't beat simple rules on
  the evals, it shouldn't be in the loop.
- **Runs locally.** The default provider is Ollama, so an 8B model on a laptop GPU is enough and no data
  leaves the machine. Anthropic and OpenAI-compatible APIs (including llama.cpp's server) are drop-in.

## Quick start

```bash
pip install -e ".[dev]"
pytest                                   # 15 tests, no model needed

gridlens generate data/events.jsonl      # synthetic stream + meter registry
gridlens summarize data/events.jsonl --registry data/registry.json -p baseline

# With a local model (https://ollama.com):
ollama pull llama3.1:8b
gridlens summarize data/events.jsonl --registry data/registry.json -p ollama
gridlens eval -p baseline -p ollama:llama3.1:8b

# Hosted models
ANTHROPIC_API_KEY=... gridlens eval -p anthropic
OPENAI_API_KEY=...    gridlens eval -p openai

# Any OpenAI-compatible server, e.g. llama.cpp
OPENAI_BASE_URL=http://localhost:8088/v1 OPENAI_API_KEY=local GRIDLENS_OPENAI_JSON_MODE=llamacpp gridlens eval -p openai

# HTTP API
uvicorn gridlens.api:app --reload        # POST /incidents/summarize
```

## Evals

`gridlens eval` runs every provider over 19 labeled scenarios generated by `synth.py`: feeder outages,
transformer faults, single-meter outages, tampering, voltage quality, communication loss, and three
**hard cases** that a fixed rule set handles badly:

| hard case | what happens | why rules struggle |
|---|---|---|
| partial phase loss | one phase of a transformer fails, a third of its meters drop together | not "most of the transformer", not "one meter" |
| sag then outage | deep sags across a transformer, then total loss of supply | mixed signals in one incident |
| lost neutral | half a transformer reports `neutral_missing` and nothing is restored | dangerous, but no single rule fires |

Scored: cause accuracy, severity accuracy, accuracy on hard cases, grounded rate, fallback rate, mean
attempts and latency.

## Layout

```
gridlens/
  events.py      event code catalog (IDIS / DLMS-style)
  grouping.py    events -> incidents with deterministic facts
  baseline.py    rule-based classifier and report (fallback + baseline)
  llm.py         Ollama, Anthropic, OpenAI-compatible providers
  summarize.py   prompt, schema validation, grounding checks, repair loop, fallback
  synth.py       labeled synthetic scenarios over a toy feeder/transformer/meter network
  evals.py       scoring harness
  api.py, cli.py
tests/           grouping edge cases, grounding, repair loop, provider outage, API
```

## Background

I build the telemetry platform behind a national smart-meter rollout (100,000+ connected meters, 300K+
Kafka messages per collection cycle). GridLens is a side project exploring how to put an LLM on top of
that kind of stream without losing the property operators care about most: being able to trust the
numbers. The data here is synthetic; no customer or utility data is used.
